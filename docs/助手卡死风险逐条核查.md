## 3. 逐条：这些代码问题会不会让游戏或电脑卡死

图例：**🔴 能直接导致卡死** / **🟠 能导致长时间无响应** / **🟡 边缘情况** / **⚪ 只是体验问题**

### 3.1 🔴 游戏冻结（最像"卡死"）、驱动 TDR、甚至整机假死：`_set_noactivate` 的自旋死锁

`Controller` 默认给浮窗加 `WS_EX_NOACTIVATE`（`app/overlay.py:214-221`）。这个标志的文档含义是"点击不激活窗口"：窗口被点击时**会返回激活失败、丢弃点击**。

但页面里又做了这些：

- 点输入框时调 `pywebview.api.activate()`（`INJECT_JS` 里 `mousedown` 分支）；
- 点搜索框后 `setTimeout(..., 150)` 再 `t.focus()`；
- 拖顶栏时 `drag_move` 是 `SetWindowPos`，但鼠标事件仍然打在浮窗上；
- 输入法候选框、自动补全等需要前台窗口派发字符的路径。

在 **独占全屏** 下，前台被游戏占着，Windows 的激活请求会失败并重试；请求者是自绘窗口（WinForms/WebView2），拿不到激活就会**反复自旋等激活完成**——表现就是：**点击浮窗 → 游戏画面冻住、鼠标不动 → 60 秒后驱动 TDR → 黑屏/掉驱动/整机卡住**。

本机 `TdrDelay=60` 正好放大了这个后果：**驱动超时不会立刻重置，而是先让整机僵住 60 秒**，这和你"感觉电脑卡死"体感完全一致。

→ **这是我认为最值得先修的一条。** 修法：呼出时用 `ShowWindow(SW_SHOWNA)` 之前先 `_set_noactivate(hwnd, False)`，**真正需要输入/拖拽/点击时不要带 `WS_EX_NOACTIVATE`**；把"不抢焦点"改为"显示后立刻把焦点还给游戏"，而不是靠这个标志。

### 3.2 🔴 插件把 F3 拦下来之后，游戏"按键不响应"：`RegisterHotKey` 抢占 F3

`Hotkey.run()` 用 **不带修饰键的 F3** 注册系统热键（`app/overlay.py:457`）。系统级 F3 是**全局独占**的：

- 游戏（包括它的 UI、画面里的功能键）**收不到 F3**；
- 如果游戏里正在输入文字，F3 会被浮窗截走（打字时按功能键 = 浮窗乱开/乱关）；
- `WM_HOTKEY` 回调是**阻塞式**的：`self._callback()` 里做 `ShowWindow / SetWindowPos / find_game_window`（要枚举全部窗口 + 查进程名），**只要它卡住，整个热键线程就卡住**，后面按多少次 F3 都排队。

→ 这是"按 F3 之后游戏像冻住了"的另一种可能。修法：热键改为 **带修饰键**（如 `Ctrl+F3` / `Alt+F3`），并且回调**只投递事件**给主线程去做，绝不在消息循环线程里做窗口操作。

### 3.3 🟠 "F3 + 自动存档 + 同步"叠加时页面重建 → 帧时间暴涨 → 驱动超时

这是你说的那个组合，代码上确实会叠在一起：

1. 游戏**在帧尾做同步自动存档**，日志明确写着 `RunFrameEndAutoSave → SaveGameWorld`：序列化 21.5ms + 加密落盘 28.6ms，**共 50.2ms，而且是在帧尾、主线程上做的**（`Player-prev.log`）。
2. 存档落盘后，助手的 `watch()` 每 2.5 秒 stat 一次，发现变化就**在主线程里跑 `render()`**（20 个模块、读 20 多份 4.8MB 存档、生成 9.6MB HTML）。
3. 生成完 `write_outputs()` 会**重写 `仙友助手.html`**；浮窗里的 WebView2 侧 `_await_page` / 页面刷新会调用 `window.load_url()` → **整页重建、重新注入 `INJECT_JS`、重设 `document.documentElement.style.zoom`**。
4. 与此同时你按 F3，浮窗 `ShowWindow` + `SetWindowPos(TOPMOST)`，在独占全屏下触发一次 DWM 合成层重建（`Player.log` 里大量 `Direct3D: detected that using refresh rate causes time drift` 就是这类事件）。

**单个 50ms 的存档不会触发 TDR（阈值 60 秒），单次 reload 也不会。** 但 4K120 + 存档加密 + 9.6MB 页面重建 + 浮窗合成切换**同时**发生，GPU 侧可能出现几百毫秒到数秒的空转/等锁——这正是 `dxgkrnl!ProcessDeadlockThread`（11-21 18:52 抓到过）会出现的形态。

→ 可行修复：
- 助手检测到**新 `.bin` 后先等 3 秒**（让游戏存档事务落定）再渲染；
- **渲染放到子进程**，页面写完后**只在浮窗收起时才 reload**，避免在画面里重建；
- 浮窗显示时暂停整页刷新（现在只"收起时暂停"，太晚）。

### 3.4 🟠 插件每帧碰游戏状态 + 外部唤醒 Wwise

`Boot.Update()`（`SaveDecryptProbe\Plugin.cs:564`）每帧都读 `Application.isFocused` / `AudioListener.pause`，失焦时调 `AkSoundEngine.WakeupFromSuspend()`。日志里 `focus=False/True` 反复出现十几次/场。

- Wwise 被游戏在失焦时主动挂起/恢复，**外部再强行唤醒**，会让回调队列在挂起窗口里被处理；`Player.log` 里 `AKASSERT: tl_uBookmarkRegionCount == 0`（Wwise 内存管理器书签计数不为 0）就是这类"不合时序的操作"留下的痕迹。
- 这类事件最坏的结果是游戏进程在 `coreclr.dll` / 原生音频线程上 **0xc0000005**（11-14 13:28 那两次正是 `coreclr.dll 0xc0000005`）。

→ 修法：**只在失焦持续 > 1 秒后唤醒一次**（现在是"失焦瞬间就召"），或者直接删掉 `KeepAudioAlive`，改成让游戏不暂停音频。

### 3.5 🟠 `watch_parent` 用 `os._exit(0)` 硬退

`app/overlay.py:327`：游戏一退，父进程 `WaitForSingleObject` 返回就 `os._exit(0)`。

- WebView2 的 `msedgewebview2.exe` 子进程来不及退出，会变孤儿；
- **崩溃标记 `xianyou_overlay_running.flag` 不会被删** → 下次启动被判定"上次崩溃"，强制软件渲染（这个标记 06:34:25 写了、06:36 游戏退出后仍在）。

累积下去就是"每玩一场多一坨孤儿进程 + 一直跑最差渲染路径"。

### 3.6 🟡 崩溃标记写入过早

`run()` 里还没 `webview.start()` 就写标记。我用本机那份 exe 实测：启动后 **<0.3 秒**标记文件就被创建（06:34:25 那次的 0.3 秒延迟就是这个）。也就是说 **WebView2 都没起来就被记成"崩溃"**，下次强制兼容模式 —— 你现在很可能是**一直**在软件渲染，并且**一直**以为开了兼容模式。修法：`webview.start()` 成功后写入，`on_closed` 时删除。

### 3.7 🟡 独占全屏下 `Application.runInBackground = true` 是非法组合

`Plugin.cs:32` 无条件设置。Unity 官方对**独占全屏**写的是"最小化时不支持 run in background"，另有 bug 报告 [`Run in Background does not work for fullscreen`](https://issuetracker-mig.prd.it.unity3d.com/issues/run-in-background-does-not-work-for-fullscreen?page=1#comments)。

效果：全屏时游戏被拉进"在后台还要出帧"的状态，Alt-Tab/浮窗时的崩溃风险显著上升（[UUM-134743](https://unityreleases.com/issues/UUM-134743) 就是这类）。→ **只在窗口化时设，全屏时删掉**。

### 3.8 ⚪（不是显卡问题）`_await_page` 的轮询与 `load_url` 黑闪

`_await_page` 每 1 秒 poll、页面就绪后 `load_url` + `show()`。页面一变就重载，重载期间 WebView 合成层丢失（`hide()` 注释里自己承认"移边缘会让 WebView2 丢合成层，恢复时黑屏"）。这解释"一会儿显示一会儿不显示"，但它**本身不会让游戏卡死**。

### 3.9 ⚪ `INJECT_JS` 的"稳定优先"样式

注入里关掉了动画/`backdrop-filter`，但每页有 `#xy-bar`、抽屉、滚动监听，且 `zoom` 每次重算。**它会增加合成负担，但不单独导致卡死。**

## 4. 结论：能不能导致"卡死游戏和电脑"

> 你补充的症状是：**每次都是有声音、没画面黑屏；两次卡到只能重启；后面几次拔掉蓝牙鼠标后按任务管理器恢复，然后 AMD 报驱动错误。** 这组症状把范围收窄了很多，见第 4.5 节。

### 4.5 "有声音但黑屏"意味着什么

这一条基本排除了"应用层卡死/Python 死循环"，因为那类卡死时声音会一起停（Wwise 在主线程上）。**有声无画＝游戏还在跑，只是渲染画面没了或被冻住**，对应的是：

1. **显示器/输出链路断了**（拔 HDMI→DP、GPU 输出端口掉、电视切输入源或 VRR 抖动）；
2. **独占全屏交换链丢失**（Alt-Tab、合成层切换、驱动重置后没能拿回画面）；
3. **显卡驱动 TDR 已发生**，D3D 设备处于"已移除"状态，DWM 用桌面背景/黑屏兜底。

而且 **"任务管理器能回来"是决定性证据**：任务管理器（DWM 合成）能弹出来，说明桌面合成器还活着，**这大概率不是整机冻结，而是那个独占全屏的 DX 设备挂了**；"拔掉蓝牙鼠标后能恢复"则说明问题集中在"输入焦点/AWE/独占切换"这条链上。

**和蓝牙鼠标的关系**：蓝牙鼠标在画面卡住时没有任何事件可查（`HidBth` 只在开机后固定写一条 `either went out of range or became unresponsive`），所以**不能说鼠标导致了卡死**。更合理的解释是：拔鼠标键鼠重连时，Windows 会做一轮焦点/输入队列重置，**这恰好会让"卡在半激活状态"的窗口回到正常**——那反而更支持 3.1（`WS_EX_NOACTIVATE` 自旋激活）这一类问题。真正的排除法需要你下次再遇到时**只拔、不关**，看画面几分钟内是否自己恢复。

### 4.6 还有一个和助手无关、但值得先排除的：远程桌面虚拟显示器

本机同时挂着两个显示适配器：

- `AMD Radeon RX 9070 XT`（`3840×2160`，正常）；
- **`OrayIddDriver Device`（向日葵远程控制的虚拟显示器驱动，状态 OK、当前在工作）**。

虚拟显示器会和物理显示器**争抢 DXGI 输出/合成目标**：独占全屏切换、显示器热插拔、远程控制接管桌面时，[`dxgkrnl!ProcessDeadlockThread`](file:///C:/ProgramData/Microsoft/Windows/WER/ReportArchive) 这类死锁正好会发生在这种"两套输出拓扑"上。**建议先禁用向日葵的显示驱动再复测**（设备管理器 → 显示适配器 → OrayIddDriver Device → 禁用），成本几分钟，能直接排除一整类原因。

## 5. 建议的修法顺序（都是小改动，不动功能）

1. **热键加修饰键**（`Ctrl+F3`），回调只投递事件。
2. **呼出时不设 `WS_EX_NOACTIVATE`**，改为显示后把焦点还给游戏窗口。
