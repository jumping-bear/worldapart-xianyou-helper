# 2.1 支线 / 红尘 / 人物志模块优化方案

> 目标：补全任务数据、彻底理清任务树、把"隐性门槛"变成玩家可见提示，
> 并在后续游戏版本更新时尽量不改代码。
> 所有结论均来自实际数据（extract_raw 原始配置表、反编译代码）与现有助手架构分析。

### 已实际排查出的遗漏清单（本次已挖，非"以后再说"）

1. **红尘任务 250 个全漏**：quest_meta 只收 type=2，type=5 一个未收，6 条女主线全部缺失。
2. **选项门槛提示缺失**：456 个带条件选项里，约 259 个是玩家属性/好感/物品/门派门槛，
   其中 126 个连游戏内灰字提示都没有（如 70253"暂且旁观"需灵机≥7、11235 需体魄/神识≥3、
   70130"动之以情"需欧冶青好感≥100、70043"买下剑谱"需灵石≥50）。助手目前一个都不提示。
3. **小蝶式反向门槛（彩蛋）**：全游戏唯一一例——入口要 NPC 境界=0、完成要≥1，
   且不给洗髓灵液就突破结丹会导致小蝶死亡。**这是孤例彩蛋，不是通用模式**，
   不要按"一类问题"过度设计，单独标记为彩蛋即可。
4. **隐藏任务普遍性**：244 个完全隐藏任务本身是设计常态，问题是助手没标注，
   玩家会把"隐藏但已触发"误判成"没触发"。这是展示问题，不是数据遗漏。

> 评审修正：初稿曾把"126 个无提示选项"笼统当成玩家门槛，其中混入了 141 个善恶击杀类
> （NPC_KILL_DEVOUR_*）和 56 个随机事件类（NPC_JEALOUS_*），这些是系统事件条件，
> 不是玩家要辛苦达成的属性门槛，优先级应降低。真正要重点提示的是约 259 个属性/好感/物品门槛。

### 三个被遗漏的根因（代码级）

1. **红尘漏收**：`app/modules/quest/build.py:370` 写死 `if quest_type == 2 or "支线" in label`，
   quest 模块的 `TABLES` 也没声明 `tbquesttype`，导致 type=5 的 250 个红尘任务整体不进快照。
2. **选项门槛不可见**：quest 模块虽读 `tbdialogue`，但只解析 `optionExpr` 里的"接取任务"调用
   来补分支；**从不解析 `optionCondition`**，所以"灵机≥7""好感≥100""灵石≥50"这类门槛
   在助手里完全没有提示。
3. **隐藏任务无标识**：`hidden=true / trackOnAcq=false / trackOnProgress=false` 的任务
   （如未竟之约 70266、小蝶近况 70267）在游戏中不进任务列表，助手也未做醒目标记，
   玩家会误以为"没触发"，实际是隐藏设计。

## 一、红尘任务：纳入任务树，做成独立精致板块

### 1.1 数据修复（先补洞）
- quest 模块 `TABLES` 增加 `tbquesttype`，`build.py` 的任务类型判定改为**从 tbquesttype 动态读取**
  所有类型（不再写死 type==2），并按 `type` 分别产出 `quests`（支线）与 `hongchen`（红尘）。
- SCHEMA 从 21 递增（数据结构变化）。这一步保证 250 个红尘任务进快照。

### 1.2 展示：独立板块，而非塞进支线
- 新增视图分区"红尘"，按 `taskGroup`（角色线）聚合为 6 条线，每条线一棵任务树。
- 复用支线模块的任务树渲染逻辑，但红尘树**单独一套更精致的样式**：
  - 角色头像 + 名称作卡片头（从 tbnpcbasecfg 取 portraitIcon）
  - 节点用带情绪色彩的分支卡片，选项分支用不同颜色标注
  - 支持折叠/展开、进度高亮
- 由于 questType 是配置表里的字段，将来新增角色线/任务**自动出现**，前端不用改。

### 1.3 触发条件同样要提示
红尘线大量节点是"传音接取"（acqCond 指向条件，如 80079 桐花传音），
且分支选项带门槛（如 80015 强硬护她需体魄≥3）。这些统一走第二部分的"条件体检"管线。

## 二、人物志模块（新增 rolebook 插件）

### 2.1 定位（评审修正：不止善恶）
以 NPC 为中心的**全息档案**，把散落在 50+ 张 NPC 表里的信息聚合成一张卡。
善恶只是其中一个维度。完整维度（均有配置表支撑）：

| 维度 | 数据字段/表 | 展示 |
|---|---|---|
| 基础 | tbnpcbasecfg：名字/头像/性别/年龄/种族/门派/境界/元素 | 卡片头 + 基础网格 |
| 性格 | propPersonality + tbnpcpersonality（14 种）+ PersonalityDesc | 性格标签 + 悬浮说明 |
| 善恶 | propEvil + tbnpcevildesc/tbalignmenttitle | 善恶色带 + 称号 |
| 声望 | propRepute + tbnpcreputedesc | 声望称号 |
| 魅力 | propCharm + tbnpccharmdesc（6 档） | 魅力评级 |
| 悟性 | initial_wisdom + tbnpcwisdomtitle | 悟性等级 |
| 亲密 | tbnpcintimacy（8 档）+ 存档好感度 | 亲密阶段进度 |
| 资质 | talent_slots + tbnpctalent（可结道侣条件） | 天赋槽/解锁条件 |
| 能力标记 | can_be_dao_companion / can_spar / can_kill / can_steal / is_merchant | 关系动作图标 |
| 互动 | tbnpcchatbubble / tbnpctopicchat / tbnpcpersuadetopic | 可聊话题/说服入口 |
| 专属内容 | 红尘线（tbquest type=5）、留影（tbmemoriaentry）、剧情（tbnpcepisode） | 关联内容入口 |

魔修"找恶名 NPC 下手"仍是核心用例之一，但只是众多筛选维度里的一个。

### 2.2 参考方案（优秀实践）
- **卡片墙 + 详情抽屉**：头像网格（1313 个有头像），点击展开全息档案，避免长列表。
- **多维筛选/排序**：善恶、境界、门派、性格、种族、是否可结道侣、是否有红尘线、可否击杀。
- **可视化**：善恶中轴色带（善→中性→恶）+ 称号；亲密阶段进度条；悟性/魅力星级。
- **风险提示**：选中 NPC 显示"攻击此人：善值+X / 恶值-Y / 城镇声望-Z / 追杀概率N%"，
  数据来自 tbalignmentattackgain 与 tbevilattackprobability。
- **"安全目标"一键筛选**：`propEvil < 0` 且 `can_kill`——魔修玩家的常用清单。
- **关联跳转**：卡片上的红尘线/留影/天赋槽可跳到对应模块详情（只传 id，不 import 模块）。

### 2.3 架构（严格遵守插件约定）
```
app/modules/rolebook/
  __init__.py   KEY/LABEL="rolebook"/"人物志"，SCHEMA=1，
                TABLES={tbnpcbasecfg, tbnpcpersonality, tbnpcevildesc,
                        tbnpcreputedesc, tbnpccharmdesc, tbnpcwisdomtitle,
                        tbnpcintimacy, tbnpctalent, tbmemoriabondtype,
                        tbmemoriaentry, tbalignmentattackgain, tbalignmenttitle,
                        tbevilattackprobability, tbreputationchangerule, tbquest}
  build.py      压缩 NPC 全息卡：基础+性格+善恶+声望+魅力+悟性+亲密档+资质+能力标记
  scan.py       按存档标注：好感、亲密进度、红尘进度（从 tables 自取，不 import quest）
  view.js/css   头像卡片墙 + 多维筛选 + 详情抽屉 + 关联跳转
```
- **不 import 其它模块**；跨模块内容（红尘/留影）靠 id 跳转或自己从 tables 取。
- 新增 NPC / 善恶规则 / 性格变化 = 配置表数据变化 → 重跑 build 即可，**不改代码**。

## 二·补、支线模块（quest）全域优化——本轮重点，非顺带

> 用户明确要求：支线模块里的**任务树、触发条件、解锁条件**等都要优化一遍。
> 这是 2.1 的核心工作量，单独列出，避免被"补红尘/建人物志"掩盖。

quest 模块现有字段（`quest_meta.json`）已覆盖：acq_cond、gate、prev/next、branch、
flow_accepts、track_ids、location 等，但存在四处"解析不全 / 表述不清"，逐项优化：

### 补.1 任务树（对应关系）
- 现状：chain/branch 已建，但 `edges` 没有统一结构，前端靠 `chain_index/branch_key` 现推。
- 优化：产出显式 `edges[]`（sequential/branch/conditional/triggered）+ `branchGroups`，
  把"分叉—汇合—隐藏接取"画清楚。验收样例=寻仙人 5 类关系自动生成（见 3.3）。

### 补.2 触发条件（triggerExpr → gate）
- 现状：`_quest_gate()` 只认 event 后第一个参数列表，且 `quests>1000` 的启发式判断易误判。
- 优化：完整解析"任务提交/进入场景/接取条件满足"三类触发，标注每个任务**由什么事件触发**。

### 补.3 解锁条件（acqCondition → acq_cond）
- 现状：`mode=unknown`（且/或嵌套）无法判定；"非(持有/完成)"这类被降级成空 kind。
- 优化：保留完整嵌套树（不只拍平），产出可读的三段式：前置条件 / 排除条件 / 判定逻辑；
  对 `mode=unknown` 明确标注"含混合逻辑，需人工确认"，不再让工具默默判不了。

### 补.4 选项门槛（optionCondition）
- 现状：完全没解析（详见第三部分）。
- 优化：解析为 P0 提示，接进 view.js 的分支卡片。

### 补.5 输出
quest 快照新增字段：`edges`、`diagnostics`、`acq_cond.tree`（完整树）、`trigger_detail`。
view.js 增加"任务树视图"和"易踩坑"筛选区（view 改动也在 quest 模块内，不碰共享文件）。

> 这一整块由 agent A 独立完成，是四个任务里最重的一个；B（红尘）、C（人物志）不依赖它。

## 三、条件体检（第4点核心，系统性挖遗漏）

### 3.1 在 quest 模块 build 阶段产出 `diagnostics`
扫描全部条件表达式与对话选项，生成结构化清单进快照，前端渲染"易踩坑提示"面板。纳入：
- **A. 混合逻辑条件**：`mode=unknown`（且/或嵌套，如未竟之约）——需人工确认括号语义。
- **B. 隐藏且必需的任务**：`hidden=true AND trackOnAcq=false AND trackOnProgress=false`
  但是其它任务的前置（如 70266/70267）——标记为"隐藏任务，列表不可见"。
- **C. 反向境界/属性门槛**：同一字段在不同环节要求相反（小蝶境界入口=0、后续≥1）
  ——这是"看着满足却完不成"的头号原因，重点标红。
- **D. 带条件的选项**：解析 `optionCondition` 引用条件表的 alias 与表达式，
  输出人话门槛（灵机≥7 / 体魄≥5 / 好感≥100 / 灵石≥50 / 需某物品）。
  - 分级处理（评审修正）：
    - **P0 玩家属性/好感/物品/门派门槛（约 259 个）**——重点提示，
      尤其 `optionGreyText` 为空的约 60+ 个，游戏里连灰字都没有，助手必须补。
    - P2 善恶击杀类（141 个 `NPC_KILL_DEVOUR_*`）——由人物志的善恶模块承载，
      对话里不必逐个提示。
    - P2 随机事件类（56 个 `NPC_JEALOUS_*`）——系统事件，低优先级。
- **E. 分支选项接取的任务**：让每条分支显示"选它需要什么"。
- **F. 隐藏任务标识**：244 个完全隐藏任务统一打"隐藏·列表不可见"标签，
  并在树里说明其触发条件，消除"没触发"的误判。

> 说明：C 类"反向境界门槛"经全量核查**全游戏只有小蝶 2 条**，属孤例彩蛋，
> 因此 diagnostics 对它做单点特殊标记即可，不必设计成通用检测规则（避免过度设计）。

### 3.2 条件语义解析（可复用，配置驱动）
- 条件表 `tbconditionexpr` 的 **alias 本身就是语义**（`LINGJI_GE_3` / `PHYSIQUE_GE_5` /
  `INTIMACY_GE_100` / `LINGSHI_GE_50` / `SIDE_ZHUJI_70253_O2`）。
- 解析优先级：alias 模式提取 → 表达式树递归翻译 → 属性名表 tbinteractattribute 映射。
- 全部规则放在 build.py，游戏新增条件=新增数据行，不写新代码。

### 3.3 任务树彻底理清
- 关系来源全部配置化：`prev/next`（tbquest）+ `optionExpr` 接取调用（tbdialogue）
  + `triggerExpr`（任务触发）+ `flow`（tbgameactionflow）+ 互斥分支（branch_key）。
- 产出统一的 `edges` 结构（供前端画树，只读不推逻辑）：
  ```
  {from, to, kind: sequential|branch|conditional|triggered, label, conditionAlias?}
  ```
  配套 `branches`（互斥组）+ `hiddenFlags`（隐藏任务）+ `diagnostics`（门槛提示）。
- 前端画树只读 edges，版本更新后树自动跟着变；click 节点展示它的条件/门槛/是否隐藏。

**验收口径（怎么算"理清了"）**——以本次排查的寻仙人链为基准样例，要求新结构能自动还原：
1. 主干 70250→70251→70252→70253 顺序边；
2. 剑下抉择 70253 分出 70254(无条件)/70255(灵机≥7) 两条 branch 边并标注门槛；
3. 两路汇合到 70258，再分 70259/70260 互斥组；
4. 70264 提交后以 triggered 边接到隐藏任务 70266，标 hidden；
5. 70266→70267 经"小蝶境界≥1"条件边，标彩蛋。
若这 5 类关系都能从配置自动生成、无需手写，即达标。

## 四、彩蛋处理（第3点）

"未竟之约"是设计给玩家的彩蛋——**不给小蝶用洗髓灵液就直接突破结丹，她会死**。
这种"剧情杀/隐藏后果"不宜做成普通任务提示（会破坏彩蛋），建议：
- 在 diagnostics 里标为 `egg=true`，默认**不剧透**；
- 玩家主动查看该任务详情时，用"隐藏结局"区块折叠展示后果与关键道具（洗髓灵液 100100）。
- 既保留彩蛋 surprise，又避免玩家误操作导致不可逆后果。

## 五、版本更新不改代码的保证（第6点）

1. **插件式模块**：新功能=新目录，自带 build/scan/view，模块间禁止 import，单个失败不影响全局。
2. **表驱动**：所有任务类型、条件、分支、善恶规则都从配置表读；build.py 只做通用解析，
   不写死具体 id/type。本次要修的"type==2 写死"正是违反此原则的技术债。
3. **SCHEMA 分模块**：数据结构变化只递增自己模块的 SCHEMA，缓存按模块隔离重算。
4. **内置快照兜底**：每个模块有 SNAPSHOT，游戏更新导致解析失败时回退内置快照，助手不崩。
5. **条件体检/人物志都是数据产物**：游戏新增角色、任务、条件=新数据行，自动进快照与 UI。

## 六、落地验收清单（可执行）

> 本章替代原"落地顺序建议"，按"模块改完即验"组织。每条含：验收动作 + 验收标准 + 证据用例编号。
> 用例编号对应 `docs/2.1验收用例.md`，逐条勾选才算该模块完成；合并前在本分支自检，合并后再跑全量回归（6.5）。

### 6.0 验收总原则
- 验收在**本 feature 分支**自检通过后才能提交；全部合并后在集成分支再跑一次 6.5 全量回归。
- 凡涉及数据结构变化（SCHEMA 递增），必须验证缓存按模块隔离重算，不得串味（见 6.6）。
- 凡"游戏更新不改代码"类结论，必须用"新增一行配置数据后 UI 自动变化"证明，不接受肉眼推断。
- 单模块失败不能拖垮全局：任一模块契约失败时其余模块仍可加载（RB-06 / REG-03）。

### 6.1 模块 A：quest 全域优化（本轮最重）
| 验收项 | 验收动作 | 验收标准（通过条件） | 用例 |
|---|---|---|---|
