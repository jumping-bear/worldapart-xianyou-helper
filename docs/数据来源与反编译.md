# 数据来源与反编译

游戏侧结论的取数顺序：**反编译代码 > 配置表 > 存档实测 > 页面展示**。
不允许只按配置字段字面含义或页面展示反推规则。

## 一、反编译产物位置

- `cpp2il_cs/DiffableCs/**/*.cs`：**只有方法签名，方法体是空 `{ }`**，不能用来判断逻辑。
- 方法体在 `_il2cpp_isil/IsilDump/<Assembly>/<Namespace>/<Type>.txt`：含 Disassembly 与 ISIL 伪指令，可按调用链读真实逻辑。
- 读逻辑的标准路径：先看调用方 → 进 ISIL 找字段读取与分支 → 回到配置表确认字段语义。

## 二、品质：两套独立编号，不能混用

- 物品品质（`Game/LubanDatas/ItemQuality.cs`）：白=0 绿=1 蓝=2 紫=3 黄=4 红=5。
- 璞石品质（`GambleStone/GambleStoneQualityUtility.cs`）：白=1 绿=2 蓝=3 紫=4 橙=5。
- 两套基准不同，按页面展示反推会错一档（璞石的白色会被当成绿色）。
  `app/output.py` 用 `QUALITY_COLORS` 与 `GAMBLE_QUALITY_COLORS` 分开定义，不要合并。

## 三、品质显示名

- 权威来源是 `tbstrconfig.ITEM_QUALITY_DICT`（`TbStrConfig` 字段，`List<L10nText>`），实测为：
  0 凡品 / 1 高品 / 2 珍品 / 3 绝品 / 4 仙品 / 5 圣品。
- `AuctionEntryTextUtil.ResolveItemQualityName` 的 ISIL：按下标取字典 → `L10nText.get_Value`；越界回退 `Int32.ToString(quality)`。
  所以前端越界应显示数字，不能编造名称。
- `ResolveItemQualitySkinKey`：quality<=1 common、2 rare、3 epic、>=4 legend，仅表现层皮肤键，不参与业务判断。

## 四、tbstrconfig 分片

- 资源里按域拆成 **24 个分片**（`tbstrconfig.<domain>.json`）。
- `meta_update._extract_tables` 只保留首个同名表，取全量键需遍历全部分片。

## 五、存档与状态语义

- 任务状态：持有=1/2/6（进行中/已完成/待提交），进行中=1，提交=3，已放弃=5。
- 条件解析会丢「非」：`gate_text/collect/evaluate` 必须保留否定；OR 只在整体失败时展示失败项，避免把未走分支当成原因。
- 任务能否在游戏列表看到取决于 `QuestFilter`（类型/状态/非 hidden），不能凭截图断言某任务不存在。

## 六、官方 Mod 体系

- 纯表补丁（`table_patch`）在当前版本不生效：目录结构、`mod.json` 声明、启用项都调过，仍无法触发配置表重载与合并。
- 唯一稳定可用的是官方化身档案（`npc.json`）。
- 官方体系内**不存在**「只改 NPC 名字、不改外观」的入口；最接近的是复制当前化身形象只改 `name.txt`。
- BepInEx 注入类方案有崩溃风险，与「绿色版、不坏档」定位冲突，不采用。
