# 2.1 并行合并与验证操作手册

> 本手册**只复述《并行开发约定.md》已定规则**在 2.1 四个并行任务上的落地，不发明新规则。
> 涉及条款均在文中标注出处，有疑义以《并行开发约定.md》原文为准。
> 适用分支：`feature/2.1-quest`（A）、`feature/2.1-hongchen`（B）、`feature/2.1-rolebook`（C）、`feature/2.1-docs`（D）；集成分支 `release/2.1`。

## 一、四条 feature 分支如何 rebase 到 release/2.1

依据《并行开发约定.md》3.1「分支角色」与 3.2「每个任务一个 worktree」：

- 每个任务在**自己的 worktree** 里开发（目录由工具链管理，日常不需手动 `new`/`remove`；手动场景用 `python tools/workspace.py list|check|new|remove`）。**不在同一个目录里切分支**——未提交改动、未跟踪模块和生成物会跟着分支串味。
- 每条 feature 分支从 `release/2.1` 切出，开发期间各自独立。
- **合并前先 rebase 到最新 `release/2.1`**（3.2）：

```
# 在各 task 自己的 worktree 内执行
git fetch origin
git rebase release/2.1
```

- rebase 后若冲突，就地解决冲突再继续，**不要强推、不要绕过**。
- 任何任务都**不改 `app/version.py`**（3.1）：版本号只在发布时由发布负责人统一修改。
- 开工前 `release/2.1` 必须是可打包基线（`python -m tools.packaging --check` 通过，3.2）。

## 二、合并顺序

依据《并行开发约定.md》3.2「合并顺序固定：模块代码 → 快照 → 版本与发布物料；后两步由发布负责人单人执行」：

| 步骤 | 内容 | 执行者 |
|---|---|---|
| 1. 模块代码 | 按 A(quest) → B(hongchen) → C(rolebook) 顺序，把三个 feature 分支合入 `release/2.1`。每合一个模块，先跑一遍该模块的自检（第三节命令 + 对应验收用例） | 版本负责人 |
| 2. 快照 | 各模块 `<key>_meta.json`（及 `EXTRA_SNAPSHOTS`）提交入库后，由发布负责人统一同步 | 发布负责人 |
| 3. 版本与发布物料 | `app/version.py`、`release/`、`仙友助手/`、`workshop_release/` 等 | 发布负责人 |

**本轮文档（D）的位置**：`docs/` 不参与运行时，按"模块代码 → 快照 → 文档"在上述第 2 步（快照）之后、第 3 步（版本与发布物料）之前由版本负责人合入，并对照《2.1验收用例.md》DOC-01 验收。第 2、3 步仍严格由发布负责人单人执行（约定硬规则）。

要点：
- 快照是**源文件、必须提交**（第四章）；刷新快照是独立动作：`python meta_update.py --export-snapshots <游戏目录> . --only <key>`。
- 主快照统一 `<key>_meta.json`，`.gitignore` 已用 `!/*_meta.json` 放行；若有非 `*_meta.json` 的额外快照，由装配负责人在 `.gitignore` 追加。
- 模块间禁止 import（第一章）：跨模块内容靠 id 跳转或从 `tables` 自取，合并时不会产生跨模块依赖冲突。
- **共享文件不改**（第二章）：`app/modules/__init__.py`、`app/tablekit.py`、`meta_update.py`、`app/render.py`、`TouchProgress.spec`、`tools/packaging.py` 等由装配负责人唯一负责，四个任务只提需求不直接改。

## 三、合并后跑哪些检查命令

依据《并行开发约定.md》3.2「合并前在自己分支跑一次……确认无功能模块加载失败」与第五章「发布前检查」。

### 3.1 每个 task 分支自检（rebase 后、合并前）
```
python xianyou_assistant.py --once --no-browser --out-dir tmp/preview
```
- 确认输出目录正常生成、**无「功能模块加载失败」**；再跑该模块对应验收用例（见《2.1验收用例.md》）。

### 3.2 每次合并一个模块后 / 全部合并后（集成分支）
```
python tools/workspace.py check       # 工作区、版本线与 tag（第五章）
python -m tools.packaging --check     # 模块契约 + 打包 datas 预演（第五章）
python xianyou_assistant.py --once --no-browser --out-dir tmp/preview  # 实跑快照
```
- `workspace.py check`：确认版本线一致、无串味/冲突告警。
- `packaging --check`：契约校验 `F*`（阻断级）必须为 0、`W*`（告警级）已确认；datas 预演通过。**任一项失败都不发布**（第五章）。
- `--once` 实跑：输出目录完整、无「功能模块加载失败」。

### 3.3 发布前最终检查（发布负责人，第五章）
```
python tools/release.py --check       # 版本一致性 / 工坊物料 / vdf 路径
```
- 三项（workspace / packaging / release）全过才发布；上传仍由人工执行 `workshop_release/upload_to_workshop.bat`。

## 四、缓存隔离注意事项

依据《并行开发约定.md》3.3「缓存隔离」：

- 源码运行时缓存按**工作区自动分开**，位置在 `%LOCALAPPDATA%\WorldApartTouchProgress\worktrees\...`，不同版本的模块数据不会互相覆盖。
- 需要指定缓存位置时设置环境变量 `XY_CACHE_DIR`。
- **打包后的 exe 仍使用原来的共享缓存**——即"源码多 worktree 隔离、打包产物共享"是预期行为，不是 bug。
- 因此：A/B/C/D 四个 worktree 各自跑 `--once` 自检不会污染彼此；但回归时若结果与预期不符，先确认当前跑的是哪个 worktree 的缓存，必要时用 `XY_CACHE_DIR` 隔离后再验。
- 数据结构变化（本次 quest 因新增 edges/diagnostics 递增 SCHEMA）只递增**自己模块**的 SCHEMA，缓存按模块隔离重算（第一章 / 方案第五章），不要手动清理其它版本的缓存来"修问题"。

## 五、一句话速查

> 各自 worktree rebase `release/2.1` → 每个 task 分支跑 `--once` 自检 → 按 模块代码→快照→文档→版本物料 顺序合并（快照与版本物料由发布负责人独做，文档在快照后合入）→ 每合一个模块跑 workspace/packaging/--once 三件套 → 发布前再跑 `release.py --check` → 全程遵守缓存按 worktree 隔离（`XY_CACHE_DIR` 可指定），不改共享文件与版本号。
